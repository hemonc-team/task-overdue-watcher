# task-overdue-watcher

Операционный «надзиратель» задач Bitrix24. Два домена за один прогон:

- **Домен 1 — просроченные задачи.** Статус открытый {2,3,4}, дедлайн в прошлом. Охват задаёт `TASK_SCOPE`: `member` (по умолчанию) — `WATCHER_USER_ID` участник в любой роли (`MEMBER`); `all` — фильтр `MEMBER` не передаётся, вебхук видит все задачи в пределах прав своего пользователя. Исполнителю — комментарий (state-машина S1/S2/S3). Self-ping (исполнитель = владелец) пропускается.
- **Домен 2 — безответные комментарии владельца.** Открытые задачи, где последний живой комментарий — от владельца и старше 2 дней. Только в отчёт, без комментов в задачу.

## Инфраструктура

- **Вебхук** — `BITRIX24_WEBHOOK_URL` в секретах Cloud Environment, к которому привязана Automation (не в git и не в тексте промпта). Scopes: `task`, `im`, `user`, и `disk`, если state лежит на Bitrix Disk. Для `TASK_SCOPE=all` вебхук создаёт **администратор портала**: Битрикс отдаёт все задачи только ему (руководитель видит подчинённых, обычный пользователь — только свои).
- **Отчёт** — `im.notify.personal.add` владельцу вебхука (`WATCHER_USER_ID`, по умолчанию 1).
- **Состояние** — `state.json` (счётчики пингов, `seeded`). В cloud **не переживает** прогон без Disk — см. шаг 0.

## Алгоритм прогона (Cursor Automation)

### Шаг 0 — state (обязательно в cloud)

Если задан `BITRIX_DISK_STATE_FILE_ID`:

```bash
python3 state_disk.py download
```

Иначе, если `STATE_FILE` указывает на существующий файл — использовать его.  
Если state нет — первый прогон будет **SEED** (без пингов).

### Шаг 1 — dry-run (первый раз после миграции)

```bash
python3 overdue_watcher.py --dry
```

Проверить stdout: число просроченных, предупреждения, режим seed/live.

### Шаг 2 — боевой прогон

```bash
python3 overdue_watcher.py
```

Скрипт сам выбирает режим: `seeded=false` → SEED (без commentitem.add), иначе LIVE.

Флаги вручную: `--dry` (read-only), `--live` (форс боевой после seed).

### Шаг 3 — сохранить state

Если `BITRIX_DISK_STATE_FILE_ID` задан:

```bash
python3 state_disk.py upload
```

### Шаг 4 — итог в чат автomation

Кратко продублировать stdout-отчёт: просрочено / пингов / эскалация / домен2 / режим (seed|live|dry).

## Логика пингов (домен 1)

| Состояние | Условие | Текст |
|---|---|---|
| S1 | просрочена, переноса не было | «Перенесите срок… и укажите причину» |
| S2 | был перенос, причины нет | «Укажите причину переноса срока» |
| S3 | перенос + причина, снова просрочена | «Срок снова истёк…» |

- Потолок **6** безответных пингов → стоп + эскалация в отчёте.
- Не чаще **1 пинга за 20 ч** на задачу.
- Бот-комменты помечены префиксом `⁣[авто-контроль]`.

## Отчёт (каждый LIVE-прогон)

- **A** — отправленные пинги (со ссылками)
- **B** — ≥2 безответных пинга, всё ещё просрочено
- **C** — мои комменты без ответа >2д
- Потолок N=6

## ⛔ STOP-GATE

- **Первый cloud-прогон без бэкапа state** → только SEED. Не форсировать `--live`, пока не перенесён старый `state.json` с `seeded: true`.
- **`TASK_SCOPE=all` на уже seeded state** — не включать. Скрипт сразу пинганёт все новые просроченные задачи портала. Сначала новый state (`seeded: false`) и один SEED, боевой прогон — со второго раза.
- **Два параллельных прогона** — `.run.lock` блокирует дубли; не запускать вручку параллельно с automation.
- **Не коммитить** `state.json`, вебхук, тексты задач в git.
